# Data dictionary

Every table in the database and every dataset the project uses: what each
field means, its units, where it comes from, and which script produces it.

**Two conventions hold everywhere.** All timestamps are stored in UTC
(`timestamptz`) and converted to Africa/Nairobi only for daily aggregation and
display. IDs are prefixed strings (`FRM-`, `NODE-`, `RD-`, `WX-`, `RSK-`,
`IMG-`, `DX-`, `ALR-`, `SYM-`) generated by `backend/ids.py`.

> **Sensor readings are SIMULATED.** The ESP32 + SHT31 node is not deployed
> yet. Everything in `sensor_readings` today was replayed from Open-Meteo by
> `tools/simulate_node.py` through the real ingest endpoint, using the JSON
> contract the firmware will use. Any result computed from sensor data is a
> result about simulated data until the node is installed, and must be
> labelled that way in Chapter 5.

### sensor_readings — **simulated until the node is deployed**

| Column | Type | Units / format | Meaning | Source |
|---|---|---|---|---|
| reading_id | text PK | `RD-xxxxxxxxxxxx` | One hourly measurement | generated on insert |
| node_id | text FK → sensor_nodes | | Which node reported it | request path |
| temperature | double | °C | Air temperature at the plot | SHT31 (simulated: Open-Meteo) |
| humidity | double | % relative humidity | Air humidity at the plot | SHT31 (simulated: Open-Meteo) |
| leaf_wetness | double NULL | sensor-specific index, unit fixed when the sensor is chosen | Optional third measurement; currently always null | future sensor |
| timestamp | timestamptz | UTC | When the reading was taken, per the node's clock | node |

`UNIQUE(node_id, timestamp)` — one reading per node per instant, which is what
makes a replayed upload harmless.

### weather_readings

| Column | Type | Units / format | Meaning | Source |
|---|---|---|---|---|
| weather_id | text PK | `WX-xxxxxxxxxxxx` | One hourly weather value | generated on insert |
| latitude / longitude | double | decimal degrees | Point requested (the site) | `SITE_LAT` / `SITE_LON` |
| source | text | `archive` \| `historical_forecast` \| `forecast` | Which API it came from | `ml/fetch_weather.py` |
| timestamp | timestamptz | UTC | The hour the value describes | Open-Meteo |
| temperature | double | °C | Air temperature, 2 m | Open-Meteo `temperature_2m` |
| humidity | double | % relative humidity | Humidity, 2 m | Open-Meteo `relative_humidity_2m` |
| forecast_issued_at | timestamptz NULL | UTC | When the forecast was issued; **always null** (see §2.3) | — |

`UNIQUE(source, latitude, longitude, timestamp, forecast_issued_at)` with
`NULLS NOT DISTINCT`, so re-fetching a range cannot duplicate rows.

### risk_scores

|---|---|---|---|---|

### diagnosis_results

| Column | Type | Units / format | Meaning | Source |
|---|---|---|---|---|
| result_id | text PK | `DX-xxxxxxxxxxxx` | One diagnosis | generated on insert |
| image_id | text FK UNIQUE → leaf_images | | The photo diagnosed (once only) | request |
| disease_label | text | `early_blight` \| `late_blight` \| `healthy` | The CNN's most likely class | `cnn_service.py` |
| confidence | double | 0–1 | Probability of that class | CNN |
| probabilities | jsonb | 0–1 per class | Full class distribution, kept for later analysis | CNN |
| risk_score_used | double | 0–1 | The weather risk r fed into fusion | `backend/fusion.py` |
| threshold_used | double | 0–1 | τ(r) that resulted | `backend/fusion.py` |
| risk_level | text | `low` \| `medium` \| `high` | Banded risk, for display | `backend/fusion.py` |

Storing `risk_score_used` and `threshold_used` on the row means any past
result can be reconstructed and explained, which is what makes the fusion
step defensible rather than a black box.

## 2. Datasets

### 2.1 PlantVillage potato subset (CNN training)

| | |
|---|---|
| Source | TensorFlow Datasets `plant_village` (54,303 images, 38 classes) |
| Data record | <https://data.mendeley.com/datasets/tywbtsjrjv/1>, DOI 10.17632/tywbtsjrjv.1 |
| **Licence** | **CC0 1.0** (public domain dedication), as stated on that record |
| Citation | Hughes & Salathé (2015), arXiv:1511.08060; Mohanty, Hughes & Salathé (2016), *Front. Plant Sci.* 7:1419 |
| How obtained | `ml/prepare_images.py --from-archive <zip>`, exporting only the 3 potato classes from the Mendeley archive (downloaded once with curl, because Mendeley refuses TFDS's downloader with HTTP 403). Only the non-augmented copy is used |
| Exported | 2,152 images: early_blight 1000, late_blight 1000, healthy 152 |
| On disk | `data/plantvillage_potato/<early_blight\|late_blight\|healthy>/*.jpg` (gitignored) |
| Splits | `data/splits/train.csv`, `val.csv`, `test.csv` — columns `filepath`, `label`; 70/15/15 stratified, seed 42, **committed** |
| Units | RGB JPEG images, 256×256 |
| Report | `docs/data_report.md` (counts, imbalance, integrity checks) |
| Caveat | Lab imagery on plain backgrounds; accuracy here is an upper bound on field performance |

### 2.2 Open-Meteo archive (ERA5) — the weather history

| | |
|---|---|
| Source | `archive-api.open-meteo.com/v1/archive`, ERA5 reanalysis |
| Licence / terms | Free for non-commercial use, no API key; ERA5 data originates from Copernicus/ECMWF |
| Coverage | 1940 → today − 5 days (ERA5 publishes with a ~5-day lag) |
| Resolution | ~25 km grid (9 km for the ECMWF IFS data from 2017), hourly |
| How obtained | `ml/fetch_weather.py --source archive` |
| On disk | `weather_readings` table (`source='archive'`) plus raw CSV in `data/weather/` (gitignored) |
| Units | °C, % relative humidity, timestamps UTC |
| Quality report | `docs/data_quality.md`, `docs/missing_hours_per_month.png` |
| Caveat | A 25 km cell smooths away the highland microclimate the node exists to measure; `ml/compare_sensor_vs_api.py` quantifies the difference |

### 2.3 Open-Meteo historical forecast — what was predicted at the time

| | |
|---|---|
| Source | `historical-forecast-api.open-meteo.com/v1/forecast` |
| Coverage | ~2022 → today (ECMWF IFS HRES back to 2017) |
| How obtained | `ml/fetch_weather.py --source historical_forecast` |
| On disk | `weather_readings` (`source='historical_forecast'`) plus raw CSV in `data/weather/` |
| Purpose | The Hutton-on-forecast benchmark: what the system *could* have said in advance |
| **Limitation** | `forecast_issued_at` is always null. This API is a continuous series stitched from the first hours of successive model runs and exposes no per-hour issue time. A true fixed-lead-time series needs the Previous Runs API (`*_previous_day1/2`, archived from 2024) or the Single Runs API (`&run=`) |

### 2.4 Simulated sensor readings — **simulated, not measured**

| | |
|---|---|
| Source | Open-Meteo hourly weather, replayed as if it came from the node |
| How obtained | `tools/simulate_node.py` POSTs to `/nodes/{node_id}/readings` with the node's API key, using the exact firmware JSON contract |
| On disk | `sensor_readings` table |
| Units | °C, % relative humidity, timestamps UTC |
| Why | The hardware comes later, and the backend, the Hutton job and the alerts all need data now. Using the real endpoint means the firmware changes nothing when it arrives |
| Caveat | These readings carry no microclimate information the API did not already have. They test the pipeline, not the sensing |

### 2.5 Field images — the farmer's weekly photos

| | |
|---|---|
| Source | Photos taken by the Kinangop farmer on his own phone |
| How obtained | Copied into `data/field_images/<label>/`, then registered by `ml/register_field_images.py` |
| Naming | `YYYYMMDD_<plot>_<seq>.jpg`, e.g. `20260921_plotA_001.jpg` |
| On disk | `data/field_images/` (images gitignored; the folder structure and `metadata.csv` are committed) |
| Metadata | `data/field_images/metadata.csv` — `image_id`, `filename`, `capture_date`, `plot_id`, `label`, `label_source` (`farmer`\|`researcher`\|`unknown`), `notes` |
| Purpose | The honest second evaluation set for the CNN: real backgrounds, real light, real phone |
| Caveat | Labels are weak. `label_source` records who decided, and unlabelled photos keep an empty label rather than a guess |

### 2.6 Farmer symptom reports

| | |
|---|---|
| Source | The farmer, through the mobile app |
| How obtained | `POST /symptom-reports` → `symptom_reports` table |
| Units | `onset_date` is a local calendar date; `notes` free text |
| Purpose | The only record of when disease actually appeared, used to sanity-check whether high-risk periods preceded symptoms |
| Caveat | Recalled after the fact, by one farmer, on one farm. Suggestive, never a validated label set |

## 3. Which script produces what

| Script | Produces |
|---|---|
| `ml/fetch_weather.py` | `weather_readings`, `data/weather/*.csv` |
| `ml/weather_quality.py` | `docs/data_quality.md`, `docs/missing_hours_per_month.png` |
| `ml/prepare_images.py` | `data/plantvillage_potato/`, `data/splits/*.csv`, `docs/data_report.md` |
| `ml/register_field_images.py` | `data/field_images/metadata.csv` |
| `ml/build_features.py` | training rows for the risk model (from daily Hutton summaries) |
| `tools/simulate_node.py` | `sensor_readings` (simulated) |
| `tools/seed.py` | the seed farmer, admin and node, and the node's API key |
| `backend/hutton.py` | `risk_scores` (`method='hutton'`) |
